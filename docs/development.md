# Устройство проекта

Панель и CLI используют произвольные профили и [общий каталог](profiles.md). `vpn-profiles` использует библиотечный режим существующего импортера и генератора. Старый BLACK/WHITE CLI обслуживает подключения без управляемого профиля. Frontend `profiles.js`/`profiles.css` не использует фреймворки; CGI возвращает типизированный JSON с ошибками и свежим снимком.

`install.sh` — публичная установка с чистыми `defaults/`, копирует только явно перечисленные файлы. Игнорируемые архивы и `router-reinstall-kit/install-on-router.sh` в личной рабочей копии — отдельное персональное восстановление, не часть публичного пакета.

`vpn-subscriptions-update` читает BLACK/WHITE manifests, обходит зеркала до первого успеха, разбирает VLESS/hy2, дедуплицирует узлы и обновляет кэш. `update/refresh` не пересобирают конфигурацию. `bootstrap` только при остановленном VPN явно загружает начальные данные напрямую. `rebuild` собирает config.json, проверяет его и перезапускает работающий sing-box. Кэш/ключи/URLs не коммитить.

`SUBSCRIPTION_FETCH_MODE` в vpn-settings.conf задает транспорт: `vpn` (default), `direct`, `vpn-first`. Последний после ошибки curl через SOCKS делает прямую попытку того же URL. `fetch_direct` отключает прокси окружения/.curlrc, привязывается к реальному uplink из main-маршрута с WAN-mark и не меняет firewall. HTTP(S) обновления при OFF не выполняются, кроме явного bootstrap. Fallback относится к ошибке загрузки, а не к успешно скачанному неподдерживаемому формату: тот по-прежнему отклоняется парсером и запускает проверку следующего зеркала.

VLESS `flow` берется только из URI: отсутствие или пустое значение не включает Vision автоматически. SNI и flow независимы; наличие REALITY/SNI не означает необходимость `xtls-rprx-vision`.

`vpnctl` предоставляет пользовательские команды. `vpn-toggle` работает с procd и маршрутизацией. Init вызывает `vpn-toggle prepare`, чтобы помеченные соединения шли через WAN в обход TUN. LAN определяется через netifd, подключенные сети — через ip. GL.iNet `route_policy` обрабатывается при наличии.

Для managed-профилей `vpn-health-check auto` делегирует `vpn-connection auto`; legacy-путь сохранен только для старых неуправляемых конфигов. Новый контроллер использует cron и краткоживущий worker под flock, не новый постоянный демон. Проверка идет через принудительный VPN SOCKS; результат хранится в `/tmp/vpn-connection/last-check.json`. Настройки в `profiles/connection-settings.json`, job/progress в `/tmp/vpn-connection/job.json`; хранится до 20 каталогов диагностики заданий, старые удаляются при следующем запуске. Подбор использует неизменяемый снимок кэша и реальные loaded-узлы, тестирует tier-ы через существующий `vpn-node-tests` по 60 (четыре параллельных HTTPS-теста), не модифицируя рабочий процесс во время поиска.

Перед переключением повторно проверяются активный профиль, SHA каталога/конфига, выбор API и версия настроек. Изменение отменяет поиск. Уже загруженный кандидат переключается native selector с `interrupt_exist_connections:false`, затем повторно проверяется. Новый кандидат при allow_reload собирает только outbounds поверх текущего config: route/DNS/inbounds не подменяются сохранёнными, но не применёнными правилами профиля. После `sing-box check` сохраняется rollback, выполняется один restart и ожидание готовности API до 15 секунд, затем проверка выбранного узла; отказ возвращает прежнюю конфигурацию. OFF-marker от vpn-toggle отменяет откат, если OFF уже виден; одновременные OFF/restart пока не сериализованы полностью (см. ревью ниже). Ручной/подобранный default сохраняется в config без рестарта; loaded-titles применяется только при совпадении полного SHA конфига.

`vpn-auto-update` читает период на каждом cron tick и обновляет кэш без применения. Плановое обновление переключается на общий каталог после активации управляемого профиля. При OFF фоновых сетевых действий нет. `sing-box-update` — opt-in обновление официального бинарника с SHA256/проверкой config, может рестартовать VPN. Архитектуры arm64/amd64/armv6/armv7; другие — SING_BOX_ARCH или ручная установка.

Панель — shell CGI + JS/CSS, отдельный LAN uhttpd, не заменяет LuCI. Новая установка использует системный пароль root, не хранит копию пароля. Настройки UCI `openwrtvpn.main`: `lan_interface`, `web_port`, `web_auth`, `modem_enabled`, `modem_apn`. После изменения привязки/модуля — restart панели. Периоды через веб применяются без рестарта VPN.

`.rules` сортируются по именам, формат документирован рядом с исходниками. Общедоступные defaults ограничены примерами; личные rules и compiled `.srs` локальны.

## Проверки и работа с роутером

Перед работой: `git status --short --branch`, затем применимые `AGENTS.md`. Публичный код и личный комплект лежат рядом: список для ревью/публикации получать через `git ls-files`, а не рекурсивным чтением всех файлов. Игнорируемые данные не добавлять в Git. Новые инструкции подкаталогов включать в явный allowlist `tests/test-publication.js` только после проверки отсутствия персональных данных.

Локальная проверка: `sh tests/run.sh` (Node.js, jq, shell и стандартные утилиты). Установщик проверяется с подменой системных путей и сервисов; updater — на синтетических архивах четырёх архитектур без скачивания и запуска настоящего бинарника. Тесты профилей, правил, подписок, диагностики и контроллера работают во временных каталогах. Для точечных изменений сначала запустить соответствующий тест, перед публикацией — общий набор и `git diff --check`.

Тесты с заглушками не подтверждают поведение BusyBox ash, procd, реального `flock`, firewall, USB или физического клиента. Рабочий роутер — не чистый установочный стенд. Сначала проверить модель, версию sing-box, статус сервиса, привязки слушателей и SHA256 изменяемых скриптов. Выводить только нужные поля; не делать полный dump UCI, config.json, syslog или подписок. `sing-box check` на рабочем конфиге может выводить секреты при ошибке: сохранять только код завершения.

Для проверки CLI без изменения подключения использовать синтетические данные и отдельные `VPN_DATA_ROOT`, `VPN_TEST_ROOT`, `VPN_CONNECTION_ROOT`; сначала проверить в исходнике, какие команды действительно соблюдают эти пути. Абсолютные вызовы init/`vpn-toggle` они не перенаправляют. Не запускать activate/on/off/update/bootstrap с фикстурами на рабочем устройстве. Синтаксис доставляемых shell-файлов проверять `ash -n`.

Перед доставкой сохранить прежние версии **каждого** заменяемого файла вне web-root с правами 700/600, проверить отсутствие активного worker и локальные инструкции. Для backend-изменений не требуется перезапуск VPN. Сравнить PID/config hash до и после, выполнить подходящий безопасный smoke-check; при сбое вернуть сохранённые файлы. Установщик целиком не использовать для обновления нескольких скриптов. Коммит/push в рабочую ветку не означает разрешение на merge.
