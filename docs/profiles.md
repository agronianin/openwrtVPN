# Произвольные профили

Данные устройства: `/etc/sing-box/profiles/catalog.json` (version 1). Здесь общий список подписок `{id,name,urls}` и профилей `{id,name,subscriptions,nodes,rules,final,preference}`. Списки профиля упорядочены. `preference`: `ru`, `non-ru`, `any`; `final`: `direct`, `vpn-out`. Подписка может участвовать в нескольких профилях. Узлы, явно добавленные в профиль, участвуют даже без включения всей подписки. Неиспользуемые источники сохраняются в каталоге, но не загружаются в активный config.json.

Кэш: `profiles/cache/<source-id>.*`. Теги узлов содержат хеш параметров подключения, поэтому перестановка строк в подписке не меняет идентификаторы. Если провайдер удалил выбранный узел, активация профиля сообщает об отсутствующем узле вместо подстановки другого по номеру. Country preference основано на названиях из подписок и является предпочтением, а не гарантией геолокации. URLTest учитывает порядок и допуск задержки; это не строгое последовательное подключение к каждому серверу.

Последний выбранный ID: `profiles/active`, признак нового управления: `profiles/managed`. При OFF профиль запоминается для включения аппаратным переключателем, но сервис остановлен и панель показывает OFF. После удаления этого профиля при выключенном VPN нужно выбрать другой. Только явная активация собирает конфигурацию. Сначала `sing-box check`, затем замена и запуск; при ошибке запуска восстанавливаются предыдущие config и состояние выбора. Нативный selector `vpn-out` переключает ручной/автоматический узел без рестарта. Повторная активация профиля сбрасывает выбор на auto.

На первом экране **Применить профиль** (раньше ↻) повторно применяет сохранённый профиль после подтверждения, с возможным кратким разрывом и сбросом ручного выбора. **Обновить состояние** — отдельная кнопка чтения состояния, без применения и тестов. Подсказки при наведении описывают различия. **Автовыбор узла** только включает native-режим `profile-auto` среди уже загруженных узлов: это не отдельный массовый тест и не обновление подписок. Во время запроса показаны действие и индикатор; после PUT команда подтверждает выбор повторным GET Clash API. Панель показывает режим, текущий узел и предупреждает, что HTTPS-доступность не проверялась. Без подтверждения — ошибка/неизвестное состояние, а не успех. Ожидание ответа ограничено 45 секундами для выбора узла (90 для остальных команд); после таймаута сначала обновить состояние, поскольку операция могла выполниться на роутере. Это не изменение механизма watchdog/безопасного поиска кандидатов.

Обновления выполняются отдельным процессом cron: `profiles/update-request`, `profiles/update-job.json`, `/tmp/vpn-auto-update.log`. Панель не ожидает долгую загрузку в CGI. В «Периоды автоматизации» задается `SUBSCRIPTION_FETCH_MODE`: `vpn` (только SOCKS VPN, default), `direct` (только реальный uplink), `vpn-first` (после ошибки загрузки через VPN одна прямая попытка того же URL). Способ применяется при следующей операции без перезапуска VPN; начатая загрузка не перенаправляется посередине. При отключении VPN оставшиеся обновления и direct-повтор отменяются; bootstrap — отдельная явная команда для OFF. Direct влияет только на загрузку, не на правила или клиентский трафик. Провайдер подписки при direct видит обычный внешний IP. Ошибка источника не удаляет старый кэш. Снимок панели читается без долгой блокировки обновлением, запись каталога атомарна с SHA256-проверкой редакции. Для правил такая же защита отдельным revision файла. Большие каталоги отображаются с поиском и ограничением числа строк.

Правила хранятся в `rule-packs/available`, выбираются/упорядочиваются профилем. Их сохранение не применяет их к текущему соединению: повторно выберите профиль. Прямой обход локальных подсетей добавляется первым, даже если соответствующий набор не отмечен. Предыдущая редакция правила хранится в `.rules.previous`; удалить используемое правило нельзя.

Команды:

```sh
vpn-profiles snapshot                 # приватный JSON, содержит адреса подписок
vpn-profiles save REVISION < data.json # атомарно заменить каталог, без рестарта
vpn-profiles check PROFILE_ID         # проверить сборку без применения
vpn-profiles activate PROFILE_ID      # применить/включить профиль
vpn-profiles activate off             # выключить, запомнив последний профиль
vpn-profiles queue-update all         # очередь загрузки через работающий VPN
vpn-profiles update all               # синхронная загрузка для CLI/cron
vpn-profiles import-cache SOURCE_ID /tmp/subscription.txt # локальный файл в существующий источник, без рестарта
vpn-profiles bootstrap PROFILE_ID     # явно разрешенная начальная прямая загрузка, только при VPN off
vpn-profiles node auto
vpn-profiles node NODE_TAG
vpn-profiles test NODE_TAG            # отдельный временный процесс; основной не переключается
```

Тест узла измеряет время HTTPS-запроса, не ICMP-пинг и не пропускную способность. Временный процесс слушает только loopback, завершается после теста. При включенном VPN его outbound имеет WAN-mark для обхода TUN. Новые зависимости/демоны не нужны.

`import-cache` принимает текстовую/base64 подписку до 16 MiB, сохраняет URL источника и не применяет данные к текущему соединению. Это позволяет скачать подписку через VPN другого устройства, передать файл по SSH и обновить существующий источник без временной замены его адреса. При неверном формате прежний кэш остается на месте. SOURCE_ID можно посмотреть в разделе Подписки. Передача файла на роутер сама по себе не загружает его узлы в активный профиль.

## Проверка узлов

В **Узлы** выберите подписку/поиск, ресурс и **Быстрый тест**. Проверяются первые 60 подходящих узлов, по четыре одновременно. На каждый — два HTTPS-запроса с таймаутом 6 секунд, результат обновляется по мере выполнения. Для 60 узлов сетевой бюджет около трех минут плюс запуск и обработка; на перегруженном роутере время может быть больше. Рабочий VPN не переключается и не перезапускается.

- **2/2**: ресурс доступен в обеих попытках. **1/2**: нестабильно. **0/2**: ресурс недоступен через этот узел сейчас.
- **HTTPS, мс** — среднее время успешного запроса с DNS, установлением туннеля и TLS. Это не ICMP ping; `time_connect` до локального SOCKS не используется как задержка удаленного узла.
- Проверяются сертификат HTTPS и точный ожидаемый HTTP-код. Редирект, 403, ошибка DNS/TLS и таймаут не считаются успехом. Ответ 403 может означать ограничение конкретного сайта, а не сломанный туннель.
- **Ресурсы проверки**: Google, YouTube и Cloudflare с ожидаемым 204; можно добавлять/редактировать/удалять свои HTTPS-адреса и ожидаемый код 200–299. Сохранение действует сразу, не меняет VPN. Выбирайте небольшой стабильный URL без авторизации. Обычная страница с кодом 200 менее показательна: она может оказаться заглушкой. Успех YouTube generate_204 не доказывает доступность видеопотоков или всей географически ограниченной функциональности.
- **Тест скорости** отдельно подтверждается: после HTTPS-проверок последовательно скачивает по 2 MiB через узлы с 2/2. Максимум 120 MiB на 60 узлов, до 6 секунд на скачивание. Источник — `speed.cloudflare.com`, не direct-домен `mirror.yandex.ru`. Скорость в Мбит/с — короткий однопоточный замер с накладными расходами, а не гарантированный максимум канала. Неполное скачивание/ошибка выводится отдельно, не превращается в фиктивную скорость.

Все запросы теста используют `socks5h` отдельного loopback-процесса sing-box с явной привязкой inbound → проверяемый outbound. Direct-резерва в тестовой конфигурации нет; WAN-mark предотвращает повторное попадание тестовых соединений в основной TUN. TLS проверяется curl без `-k`, пользовательский `.curlrc` не читается. Основной selector не трогается. Результат характеризует узел из кэша и выбранный ресурс, не всю маршрутизацию Wi-Fi-клиентов. Страна/город в строке взяты из названия подписки, не из независимой геопроверки.

Если кэш обновился после открытия панели, устаревшие теги не подменяются узлами с похожими названиями: тест возвращает ошибку. Нажмите обновление состояния и повторите выбор. Автоматический полный обход соблюдает заданный интервал и после частичной ошибки, а не повторяется каждую минуту; занятая блокировка не считается выполненной попыткой. Ручное обновление остается доступным отдельно.

CLI: `/usr/bin/vpn-node-tests targets`, `targets-save REV` (JSON-массив на stdin), `start` (stdin: `{"tags":["NODE_TAG"],"target":"youtube","speed":false}`), `status JOB_ID`. Настройки: `/etc/sing-box/profiles/test-targets.json`; фоновые результаты и диагностика: `/tmp/vpn-node-tests/JOB_ID/`, до перезагрузки. Одновременно выполняется только один тест, второй получает явную ошибку. Он не выбирает и не исключает узлы автоматически. Штатные URLTest/watchdog остаются отдельными механизмами.

Основа: [sing-box URLTest](https://sing-box.sagernet.org/configuration/outbound/urltest/), [параметры curl](https://curl.se/docs/manpage.html). Наличие успешного TCP handshake само по себе недостаточно для проверки VLESS/REALITY и доступа к сервису.

Миграция выполняется один раз без перезапуска старого VPN. BLACK и WHITE превращаются в два начальных профиля; существующий каталог не перезаписывается. Старые команды `vpnctl mode/subscription` нельзя смешивать с новыми профилями после активации; CLI выдает ошибку вместо скрытого изменения старого режима. `vpnctl status check` остается диагностикой, хотя его старые подписи BLACK/WHITE не являются источником истины для новых профилей.

Откат конкретного устройства выполняется из его backup до миграции. Сначала выключить новый VPN, сохранить новые пользовательские данные, вернуть предыдущие CGI, JS/CSS и скрипты из backup. Вернуть прежний config.json и настройки выбора; каталог `profiles` переименовать (не удалять), чтобы старый cron не выбирал новый updater. На рабочем устройстве не запускать полный установщик ради отката.
