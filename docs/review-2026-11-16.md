# Ревью OpenWrtVPN — 2026-11-16

Проект управляет VPN одного OpenWrt-роутера через shell CLI, cron и отдельную веб-панель. Ревью рассчитано на домашнюю LAN, несколько клиентов панели, сотни узлов подписок и одновременную работу cron/ручных команд. Проверены основные пути установки, обновления, импорта, сохранения профилей, диагностики, переключения и отката; модем — границы opt-in, без смены USB/AT-настроек.

Исходная точка: `d94301f`, ветка `codex/vpn-recovery`. Изменения ревью находятся в отдельной `codex/project-review`; merge в main не выполнялся.

## Существенные проблемы

1. **P1 — обход каталога правил через перевод строки. Исправлено.** В `vpn-profiles:valid_id` и `vpn-node-tests:valid_id` построчный grep принимал многострочный ID, если одна строка соответствовала шаблону. Через `rule-save` можно было создать `.rules` за пределами каталога правил от root. Теперь проверяется всё значение; каталог JSON валидируется до преобразования в строки и должен содержать ровно один документ. Тесты отвергают traversal с LF, URL с LF и несколько JSON-документов без сохранения.

2. **P1 — токены подписок в логах при обычном отказе зеркала. Исправлено.** `vpn-subscriptions-update:try_refresh_group_url` передавал полный URL в stderr/syslog. Теперь сообщение содержит название источника и номер зеркала; сырой stderr загрузчика не публикуется. Регрессия проверяет отсутствие секретной части URL и при сетевой ошибке, и при неправильном формате. Уже существующие журналы этим изменением не очищаются.

3. **P1 — несогласованные настройки поиска и разрешение restart. Исправлено.** `vpn-connection` читал настройки и их ревизию отдельно: задание могло получить старое разрешение на restart с новой ревизией. Теперь ревизия вычисляется из того же снимка; финальная проверка контекста и применение используют общий lock с сохранением настроек. Изменение запрета во время `sing-box check` отменяет применение. Это не устраняет отдельную гонку жизненного цикла из пункта 4.

4. **P1 — OFF и параллельный restart не сериализованы полностью. Открыто.** В `vpn-connection:rollback_config` между проверкой off-marker и вызовом restart может завершиться `vpn-toggle off`; после этого restart вновь запустит сервис. Аналогично пересекаются активация профиля и ручные on/off. Нужна общая короткая блокировка управления жизненным циклом, согласованная с procd, активацией профиля и откатом; lock только внутри одного worker или ещё одна проверка маркера не закрывают окно. В этом проходе не менялась вся схема запуска сервиса. Не воспроизводилось на рабочем устройстве, чтобы не оборвать сеть; вывод подтверждается последовательностью вызовов в исходниках. Пока не исправлено, избегать одновременных команд питания VPN и применения профиля/отката из разных клиентов.

5. **P1 — откат выбора отключался до записи конфига. Исправлено.** При отказе записи `.new` после успешного selector PUT задание завершалось ошибкой, но оставляло новый узел активным. Теперь откат остаётся включённым до обязательного сохранения default. Тест моделирует недоступный путь записи и проверяет возврат старого selector и неизменность конфига. Сообщения об отказе больше не объявляют восстановление успешным до его выполнения.

6. **P2 — неконтролируемое накопление диагностики в RAM. Исправлено.** На устройстве `/tmp/vpn-node-tests` занимал около 89 МиБ, `/tmp/vpn-connection` — около 6,6 МиБ. Оба компонента теперь сохраняют до 20 каталогов заданий и очищают старые при следующем запуске под блокировкой. Внутренние результаты тестов автоподбора удаляются после чтения; тесты проверяют лимит даже при переводе часов назад. Это ограничение числа задач, не строгая квота в байтах; большие отдельные подписки всё ещё требуют RAM.

7. **P2 — тестировался другой outbound с тем же тегом; пользовательская цель проверки терялась. Исправлено.** Объединение cache и loaded предпочитало кэш, а переключение selector использовало загруженный узел. Теперь loaded имеет приоритет в обоих путях. Изолированный подбор получает снимок выбранной цели проверки, включая пользовательскую; раньше он знал только стандартные цели. Поведение покрыто регрессиями.

8. **P2 — ошибки JSON и ложный успешный статус CLI. Исправлено.** URI с управляющими символами, например TAB в WS path, давал некорректный JSON; экранирование теперь выполняет jq. `vpn-toggle on/off` возвращал успех при отказе сервиса из-за последующего успешного log; теперь итоговое состояние проверяется и ошибка возвращается вызывающему коду. Тесты не запускают реальные сервисы.

9. **P2 — неполный backup и неправильная архитектура обновлятора. Исправлено.** `install.sh` не сохранял прежние `vpn-profiles`, `vpn-node-tests`, `vpn-connection`. Они добавлены в backup, установленный auth-файл панели сохраняется при повторной установке. `sing-box-update` выбирал архив по архитектуре, но искал внутри только arm64: путь теперь берётся из имени архива. Sandbox-проверки покрывают backup, сохранение auth и четыре архитектуры, без скачивания настоящих релизов.

## Инструкции и документация

10. **P2 — агентам не хватало воспроизводимого безопасного порядка проверки. Исправлено.** Корневой `AGENTS.md` уже правильно разделял публичные/личные файлы и запрещал изменения сетевой конфигурации, но не объяснял ограничения тестов, диагностику секретов и временные данные. Добавлены `tests/AGENTS.md`, раздел проверок в `docs/development.md`, требования к валидации целого ID, безопасным логам, backup и ограничению `/tmp`. Publication-check явно разрешает новый файл инструкций; запуск проверки публикации теперь работает и в Git worktree, где `.git` — файл. В документации убрана абсолютная гарантия защиты OFF, которой реализация не обеспечивает.

## Проверки и устройство

- До изменений и после них прошёл `sh tests/run.sh`; новые проверки воспроизводят перечисленные исправления. Пройден `git diff --check`. Publication-check повторно прошёл после staging: 58 публичных файлов, без персональных manifest, ключей и локальных путей.
- На GL-BE3600 проверены работающий sing-box 1.14.4, валидность его конфигурации без вывода секретов и привязки портов: панель только LAN, API/SOCKS только localhost.
- Для шести изменённых CLI прошёл синтаксис BusyBox ash на самом устройстве. На изолированных синтетических данных прошли создание каталога профилей, сохранение правила, отказ ID с LF и чтение целей проверки. Начальную фикстуру пришлось дополнить пустым config и каталогом правил; рабочие файлы эти прогоны не затрагивали.
- По явному запросу владельца включена авторизация панели с отдельным паролем и логином `root`. Неавторизованный запрос получил HTTP 401, авторизованный — 200. Системные пароли, PID и config VPN не изменились. Пароль и хеш в репозиторий не записаны.
- Шесть CLI доставлены после завершения активного подбора (334 узла), под блокировками подписок, соединения, тестов узлов и настроек. Прежние файлы сохранены, установленные файлы сверены с исходниками; PID/config VPN при доставке не изменились. Пути персональных backup записаны только в локальных инструкциях.
- После доставки проверка текущего соединения завершилась сначала с 1/2, при повторе с 2/2. Изолированный тест того же узла к той же Google-цели дал 0/2, `SSL connection timeout`; причина расхождения не установлена. Правило рабочего SOCKS действительно направляет проверку в `vpn-out`. Это наблюдение о стабильности реального подключения, а не доказанная ошибка нового кода. Оба теста сохранили PID и config VPN.
- Очистка на следующих проверках уменьшила `/tmp/vpn-node-tests` до примерно 12 МиБ и `/tmp/vpn-connection` до 3,2 МиБ.

Итог: основная архитектура подходит этому масштабу; новый фреймворк или зависимости не нужны. Приоритет следующего исправления — единый порядок запуска/остановки из пункта 4.

Не проверены: чистая установка на физическое устройство, реальный сбой WAN/питания, параллельные OFF/restart на живой сети, IPv6 и отдельный физический LAN-клиент, смена режимов модема, настоящие обновления бинарника на amd64/armv6/armv7. Все legacy-команды `vpnctl` и все DOM-сценарии вручную не проходились; это целевое ревью рискованных путей, не доказательство отсутствия остальных ошибок.
